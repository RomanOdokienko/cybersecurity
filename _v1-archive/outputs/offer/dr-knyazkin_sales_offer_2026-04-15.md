# Экспресс-аудит безопасности сайта dr-knyazkin.ru
Дата: 15 апреля 2026  
Формат: пассивный аудит публичных данных (без активных атак)

## Итог для руководителя
Сайт работает стабильно и визуально аккуратно, но есть 4 зоны риска, которые дают понятную бизнес-ценность для доработки:
1. Защита email-домена (SPF/DMARC/DKIM) не настроена.
2. Базовые security headers неполные.
3. Риски внешних скриптов (без SRI) + устаревший jQuery.
4. На формах есть ссылка на политику, но URL политики в публичной проверке отвечает `403`.

Это не “аварийный инцидент”, но хороший кейс для апсейла на hardening + compliance-пакет.

## Приоритетные проблемы (что продаем на демо)

### P1. Email-защита домена не настроена
Факт:
- Не найдены TXT-записи SPF/DMARC/DKIM (default/google/mail), а также MTA-STS/TLS-RPT.

Риск для бизнеса:
- Возможна подмена писем от имени клиники (фишинг, репутационные потери, жалобы пациентов).

Что делать:
- Внедрить SPF (`-all`), DMARC (минимум `p=quarantine`), DKIM.
- Вторым этапом включить MTA-STS и TLS-RPT.

### P1. Неполный baseline security headers
Факт:
- Отсутствуют: `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- Присутствует только `X-Frame-Options`.

Риск для бизнеса:
- Повышенная поверхность атак и ниже уровень базовой защищенности.

Что делать:
- Включить baseline заголовков на веб-сервере/CDN.
- Донастроить CSP по whitelist после короткого периода мониторинга.

### P1. Supply-chain риск фронтенда
Факт:
- На главной странице: 25 внешних скриптов без `integrity` (SRI).
- Обнаружен `jQuery 1.10.2` (устаревшая ветка).

Риск для бизнеса:
- Риск компрометации через сторонний JS и техдолг, влияющий на стабильность/безопасность.

Что делать:
- Обновить jQuery до актуальной поддерживаемой версии.
- Добавить SRI для внешних ресурсов, где это возможно.
- Уменьшить число внешних зависимостей.

### P2. Комплаенс формы/политики
Факт:
- На формах есть маркеры согласия и ссылка на `/politika`.
- При внешнем запросе `https://dr-knyazkin.ru/politika` возвращается `403 Forbidden`.

Риск для бизнеса:
- Риск претензий по юридической прозрачности обработки персональных данных.

Что делать:
- Обеспечить стабильную публичную доступность страницы политики.
- Проверить корректность связки “форма -> чекбокс согласия -> текст политики”.

### P2. Поведение `www`-хоста
Факт:
- `https://www.dr-knyazkin.ru/` в проверке отдавал `403`.
- `http://www...` делает редирект на канонический `https://dr-knyazkin.ru/`.

Риск для бизнеса:
- Непредсказуемое поведение для части пользователей/ботов/мониторингов.

Что делать:
- Унифицировать поведение `www` и `non-www` под единый сценарий.

## Что уже в норме
- TLS-сертификат валиден (`Let's Encrypt`, SHA-256, ~37 дней до истечения на дату проверки).
- HTTP -> HTTPS редирект на основном хосте настроен (`301`).
- Явного mixed content на главной не обнаружено.
- `robots.txt` и `sitemap.xml` доступны.

## Предложение на демо (апсейл)
На демо показываем:
1. Дорожную карту фикса на 14/30 дней.
2. Приоритизацию “быстрые победы vs инфраструктурные изменения”.
3. Финальный целевой baseline для клиник (без перегруза командой разработки).

Ожидаемый результат:
- Быстро снизить технический и репутационный риск.
- Закрыть комплаенс-дыры по форме/политике.
- Поднять доверие к бренду и устойчивость маркетинговой воронки.

## Ограничения проверки
- На части URL активна антибот-защита (`ddos-guard`, ответы `403/429`), поэтому часть выводов требует точечной валидации на демо с доступом к инфраструктуре.
