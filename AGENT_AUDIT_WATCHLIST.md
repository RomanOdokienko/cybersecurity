# Agent Audit Watchlist

Версия: 2026-05-15

Цель: фиксировать типовые сбои и единые правила трактовки, чтобы каждая следующая проверка клиники не застревала на одних и тех же местах.

## Как использовать

1. Перед проверкой клиники пройти `Preflight` (ниже).
2. После заполнения `agent_structured` пройти `Post-check`.
3. Если встречен новый типовой сбой: добавить его в этот файл в секцию `Новые паттерны`.

## Preflight (перед стартом 1 клиники)

1. Проверить режим: `AGENT_ONLY_MODE.lock` должен содержать `mode=agent_only`.
2. Проверять только одну клинику за проход.
3. Не использовать предзаполненные значения как итог: финал только из свежего агентного просмотра.
4. Сразу определить целевые страницы для обхода:
   - главная;
   - цены;
   - врачи/специалисты;
   - документы/правовая;
   - политика ПДн;
   - контакты.

## Post-check (перед сохранением JSON)

1. Убедиться, что `agent_structured` заполнен по всем 3 блокам.
2. Для полной проверки выставить `verification.b1/b2/b3 = true` и `verification.mode = agent`.
3. Проверить кодировку:
   - в `metric/status/poc` нет `????`;
   - значения статусов только из рабочего словаря (`ок`, `проблема`, `проверить`, `н/п`).
4. Проверить, что PoC ссылается на реальные страницы сайта, а не fallback-пути.
5. Проверить, что обновлена только текущая клиника (JSON + ее detail + ее строка в таблице).

## Типовые проблемы и правила трактовки

### 1) Policy URL дает 403 в low-level запросе, но страница читается в браузере

Симптом: `requests/curl` видит 403, но в браузерном режиме политика открывается.

Правило:
- Не считать это "политики нет".
- Для финального вывода по policy-метрикам использовать браузерный факт и PoC с читаемым текстом.

### 2) Ложный сигнал по `meta`

Симптом: найдено слово `meta`, но это HTML-тег `<meta>`.

Правило:
- `<meta ...>` не относится к запрещенной организации.
- Учитывать только релевантные сущности: `facebook.com`, `instagram.com`, `Meta Platforms` в осмысленном контексте.

### 3) Упоминание `facebook.com` только в кодовом шаблоне

Симптом: токен есть в JS/шаблоне, но нет явной публичной ссылки на странице.

Правило:
- Фиксировать как кодовое упоминание в PoC.
- Если по методологии любое упоминание считается нарушением, ставить `проблема`.
- Если позже методология разделит "код" и "видимый линк", этот кейс переключается без изменения формата JSON.

### 4) Cookie-баннер найден, но это не текст политики

Симптом: фраза про `Яндекс.Метрика` есть в глобальном cookie-тексте, но в теле политики нет.

Правило:
- Разделять источники:
  - `policy_body` (текст самой политики);
  - `global_cookie_banner`.
- Для метрики "Яндекс.Метрика ... в политике" опираться именно на `policy_body`.

### 5) После 26-й клиники блок 1 исторически мог быть предзаполнен

Симптом: в UI/JSON видны старые значения, но полной новой проверки не было.

Правило:
- Для клиник 26+ не использовать исторический prefill как итог.
- До полной агентной проверки статусы считаются не подтвержденными.

### 6) Частичная верификация вместо полной

Симптом: часть метрик обновлена, но `verification` отмечен как будто проверено все.

Правило:
- Полная проверка = полный агентный проход по 3 блокам + `b1/b2/b3=true`.
- Иначе блок остается не верифицированным.

### 7) Сбой кодировки при записи JSON

Симптом: `metric/status` превращаются в `????`.

Правило:
- Запись только UTF-8.
- Перед сборкой прогнать быструю проверку на `????` и битые статусы.
