# Agent Validation Protocol (Blocks 1-3)

Версия: 2026-05-08

## Цель

Скрипт не является источником истины по метрикам.  
Скрипт собирает сырьё (URL, HTML, сигналы), агент выносит финальный бинарный вердикт.

Финальный статус метрики (`ок`/`проблема`) ставится только после агентной проверки.

## Роли

1. `scripts/audit_site.py`:
- собирает raw evidence;
- не является финальным судьёй по спорным/семантическим метрикам.

2. Агент:
- проверяет сайт по методологии и по смыслу;
- при необходимости добирает данные сам (не ограничивается скриптовыми URL/хинтами);
- фиксирует PoC и ставит бинарный вердикт.

3. `scripts/build_dashboard.py`:
- отображает результат;
- блок считается «проверен», только если выставлен флаг агентной верификации.

## Обязательный pipeline на 1 клинику

1. Запустить скриптовый сбор evidence.
2. Агент проверяет метрики блока на сайте по методологии (включая спорные кейсы).
3. Агент формирует PoC по каждой метрике:
- URL;
- что найдено;
- почему это `ок` или `проблема`.
4. Только после этого ставится `verification.<block>=true`.
5. Пересборка дашборда.

## Главный принцип качества

`script_signal = hint`, `agent_evidence = ground truth`.

Если скрипт и агент расходятся:
- в таблицу идёт агентный вердикт;
- в PoC сохраняется, что именно проверил агент.

## Правила бинарности

1. Разрешённые статусы метрик: только `ок` или `проблема`.
2. Если доказательств недостаточно, блок не помечается как верифицированный.
3. Нельзя «авто-проставлять» метрики по не-проверенным клиникам.

## Минимальные требования к PoC

Для каждой метрики:
- `evidence_url` (или список URL),
- краткий факт (1-3 строки),
- итоговый `status`.

Формат текста свободный, но должен быть проверяемым вручную.

## Антипаттерны (запрещено)

1. Считать блок проверенным только потому, что скрипт отдал “ок”.
2. Делать финальный вывод по fallback-эвристикам без агентной проверки.
3. Ставить массовые значения в блоках 2/3 по всему списку без по-клиентной верификации.

## Что это даёт проекту

1. Масштабируемость: агент может распознавать нестандартную структуру сайтов.
2. Повторяемость: методология фиксирована, PoC прозрачен.
3. Контроль риска: снижаются ложные `ок`/`проблема` от узких regex/хинтов.
